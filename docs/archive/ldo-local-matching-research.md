# Pretrained local matching components for LDO

Research date: 2026-10-03. Scope: image-pair correspondence components for EuRoC stereo monochrome keyframes, with an existing visual–inertial estimator and loop backend. Research only: no model was installed, downloaded, executed, trained, or measured on this machine. Statements about suitability and integration below are design recommendations, not EuRoC benchmark results.

## Recommendation

Start with the released **SuperPoint + LightGlue** pipeline as the sparse baseline, and **EfficientLoFTR full** as the complementary detector-free baseline. This tests whether missed geometric evidence comes from sparse detection/description or from matching itself. Evaluate pretrained weights before considering fine-tuning. LightGlue takes independently extracted local features; EfficientLoFTR establishes correspondences from a pair of images. Both have released inference code and checkpoints. [LightGlue repository](https://github.com/cvg/LightGlue), [EfficientLoFTR repository](https://github.com/zju3dv/EfficientLoFTR)

If the original SuperPoint license is unsuitable, **ALIKED + its matching LightGlue checkpoint** is the immediate sparse alternative: ALIKED's source is BSD-3-Clause and LightGlue has a released ALIKED feature configuration. The bundled ALIKED extractor converts a one-channel tensor to RGB internally. This alternative should receive its own EuRoC comparison; license compatibility does not imply equivalent matching performance. [ALIKED source and license](https://github.com/cvg/LightGlue/blob/main/lightglue/aliked.py), [ALIKED project](https://github.com/Shiaoming/ALIKED), [LightGlue feature configuration](https://github.com/cvg/LightGlue/blob/main/lightglue/lightglue.py)

Use **RoMaV2** as the stronger dense comparator if GPU resources permit; retain original **RoMa indoor** as a useful comparison with a simpler DINOv2 license chain. Treat **MatchAnything** as an additional appearance/domain robustness experiment after these baselines. Its emphasis on unseen cross-modality registration does not establish superiority for two visits recorded by EuRoC's same monochrome cameras. This ranking is an integration judgment, not a universal accuracy ranking. [RoMa model constructors](https://github.com/Parskatt/RoMa/blob/main/romatch/models/model_zoo/__init__.py), [RoMaV2 paper](https://arxiv.org/abs/2511.15706), [MatchAnything paper](https://arxiv.org/abs/2501.07556)

These components produce **correspondences**, not a complete loop detector. Keep global candidate retrieval as a separate stage, then run local matching on shortlisted pairs and feed numerical geometric evidence to LDO's proposal policy. A local match count or average confidence is not automatically a loop probability. This boundary follows the published input/output interfaces below and is consistent with the proposed [local detector topology](loop-detector-topology.md).

## Verified interfaces and practical differences

| Component | Published input → output | Reuse and suitability for LDO |
|---|---|---|
| SuperPoint + LightGlue | SuperPoint: image → sparse keypoints, detector scores, 256-dimensional floating descriptors. LightGlue: each image's keypoints/descriptors/image size → match indices and scores. | Cache per-keyframe SuperPoint features; reuse across candidates. Explicit keypoint IDs make evidence easy to track. SuperPoint is a CNN; LightGlue supplies the transformer matcher. [Extractor source](https://github.com/cvg/LightGlue/blob/main/lightglue/superpoint.py), [matcher source](https://github.com/cvg/LightGlue/blob/main/lightglue/lightglue.py) |
| EfficientLoFTR | Two one-channel image tensors → `mkpts0_f`, `mkpts1_f`, `mconf`. | Produces semi-dense, subpixel correspondences without an external keypoint detector. Pair-conditioned attention means final features/matches depend on both images. [Official usage](https://github.com/zju3dv/EfficientLoFTR#match-image-pairs-with-efficientloftr), [paper](https://arxiv.org/abs/2403.04765) |
| RoMa | Two images → dense normalized warp and certainty; sampling → paired points; coordinate conversion → pixels. | Dense correspondence evidence; released indoor/outdoor constructors. Backbone features can be extracted separately internally, but the public example is pair matching. [Usage](https://github.com/Parskatt/RoMa#demo--how-to-use), [constructors](https://github.com/Parskatt/RoMa/blob/main/romatch/models/model_zoo/__init__.py) |
| RoMaV2 | Two images → forward/backward warp, overlap and precision maps; `sample` → correspondences, overlap scores and endpoint precision matrices. | Adds image-coordinate uncertainty estimates. Current default constructor fetches `romav2.0.1.pt`; released `forward` asserts inference mode. [Inference source](https://github.com/Parskatt/RoMaV2/blob/main/src/romav2/romav2.py) |
| MatchAnything | Author demo exposes `matchanything_eloftr` and `matchanything_roma`; image pairs → paired pixel coordinates and `mconf`. | Alternative pretrained weights for ELoFTR/RoMa architectures. Training code is still promised later in the current official GitHub README. [Official release note](https://github.com/zju3dv/MatchAnything), [author inference wrapper](https://huggingface.co/spaces/LittleFrog/MatchAnything/blob/main/imcui/hloc/matchers/matchanything.py) |

The original RoMa paper uses frozen DINOv2 features for robust dense matching. RoMaV2 uses frozen DINOv3 features, a multiview transformer matcher, and CNN refinement. Thus a requirement for a transformer-based component does not imply that every stage in these pipelines is a transformer. [RoMa paper](https://arxiv.org/abs/2305.15404), [RoMaV2 paper, architecture](https://arxiv.org/html/2511.15706v3#S3)

## Grayscale, resolution and coordinate contracts

EuRoC provides WVGA monochrome stereo images at 20 Hz and calibrated cameras/IMU; exposure is controlled independently for each camera, so synchronized stereo brightness can differ. The local installation records 752 × 480 sensor images. Grayscale compatibility does not establish robustness to motion blur, repeated structures, or this exposure behavior. [ETH dataset description](https://projects.asl.ethz.ch/datasets/euroc-mav/), [installation note](euroc-dataset.md)

- **SuperPoint:** accepts a one-channel input and converts three-channel input to grayscale. Use float image values in `[0,1]`. The convenience extractor resizes by default; `extract(..., resize=None)` disables resizing, and its returned keypoints are mapped back to input-image coordinates. Preserve that coordinate convention. [SuperPoint source](https://github.com/cvg/LightGlue/blob/main/lightglue/superpoint.py), [preprocessing source](https://github.com/cvg/LightGlue/blob/main/lightglue/utils.py)
- **EfficientLoFTR:** official example uses grayscale `[1,1,H,W]` tensors divided by 255, with dimensions divisible by 32. Its simple resize floors dimensions, so 752 × 480 becomes 736 × 480; restore coordinates using the documented per-axis resize mapping before stereo/XYZ lookup. The `full` and `opt` modes share the released outdoor checkpoint; reparameterization is required for its efficient inference path. The repository warns that MegaDepth training creates an indoor domain gap. [Official README](https://github.com/zju3dv/EfficientLoFTR#match-image-pairs-with-efficientloftr)
- **RoMa:** path loading converts to RGB. Tensor input requires three channels, and its direct tensor path checks dimensions divisible by 14. Replicate the monochrome channel into three channels; this satisfies the interface without inventing color information. Public defaults use 560 × 560 coarse resolution and 864 × 864 upsampling. [Input-check source](https://github.com/Parskatt/RoMa/blob/main/romatch/models/matcher.py), [resolution settings](https://github.com/Parskatt/RoMa#settings)
- **RoMaV2:** paths convert to RGB, arrays/tensors require three channels, and `uint8` values are scaled by 255. Replicate grayscale for array/tensor use. The current default `precise` setting resizes to 800 × 800 and 1280 × 1280; `base`, `fast`, and `turbo` use 640, 512, and 320 square resolutions without the high-resolution pass. These are published settings, not choices already validated for LDO. [Loading and settings source](https://github.com/Parskatt/RoMaV2/blob/main/src/romav2/romav2.py)
- **MatchAnything:** the linked author wrapper keeps original RGB-shaped tensors, creates grayscale tensors with resize/padding divisible by 32, and returns keypoints plus `mconf`. It rescales ELoFTR output to original pixels. Its checked-in initialization currently raises `NotImplementedError` for non-CPU `DEVICE`; the wrapper therefore needs inspection before GPU reuse even though the project reports CUDA testing. [Wrapper source](https://huggingface.co/spaces/LittleFrog/MatchAnything/blob/main/imcui/hloc/matchers/matchanything.py), [author setup README](https://huggingface.co/spaces/LittleFrog/MatchAnything/blob/main/imcui/third_party/MatchAnything/README.md)

**LDO adapter recommendation:** document whether matcher pixels refer to raw sensor images, rectified images, resized tensors, or padded tensors. Store the mapping to the existing stereo geometry domain. Never combine a resized/rectified match coordinate with the wrong intrinsics, rectification map, or camera axes. Assign matcher-specific observation IDs; new matches do not inherit exported ORB row identities. The current native ORB identity and raw/rectified mapping are defined in [ORB XYZ evaluation](orb-xyz-evaluation.md).

## Native ORB descriptors: no direct pretrained replacement

LightGlue's supplied feature families include SuperPoint, DISK, ALIKED, SIFT, DoGHardNet and raco-ALIKED, with family-specific learned weights and input dimensions. ORB is absent. The maintainer explicitly states that weights trained for one descriptor kind are incompatible with other descriptors, including differently trained SuperPoint implementations. Casting ORB's packed bytes to float, unpacking 256 bits, padding, or inserting a linear projection cannot establish compatibility with pretrained SuperPoint-LightGlue. [Supported feature configurations](https://github.com/cvg/LightGlue/blob/main/lightglue/lightglue.py), [maintainer explanation](https://github.com/cvg/LightGlue/issues/83)

EfficientLoFTR, RoMa and MatchAnything take images; they do not accept native ORB descriptors as the external pretrained matching representation. RoMa's `match_keypoints` can associate arbitrary supplied keypoint locations through its image-derived dense warp. This could associate ORB **locations** with a predicted warp; it still uses new learned image features rather than ORB descriptor matching. Treat any such association as a separately evaluated mapping with a tolerance and ambiguity policy. [RoMa API](https://github.com/Parskatt/RoMa#demo--how-to-use), [RoMa matching source](https://github.com/Parskatt/RoMa/blob/main/romatch/models/matcher.py)

A matcher specifically trained for ORB could be an LDO research project. Glue Factory supports training LightGlue on custom local features, but no supplied ORB checkpoint was verified. Retaining upstream ORB identity versus introducing independent learned keypoints is a design decision; pretrained compatibility must not be inferred from matching descriptor dimensions. [Glue Factory](https://github.com/cvg/glue-factory)

## Compute and checkpoint caveats

| Published measurement | What it establishes | What remains to measure |
|---|---|---|
| LightGlue: 150 FPS at 1024 keypoints on RTX 3080 with compilation/adaptivity; CPU 20 FPS at 512 keypoints on i7-10700K. | Matcher throughput under stated settings. [Official benchmark](https://github.com/cvg/LightGlue#benchmark) | Extraction, image preparation, cache transfers, each candidate pair, and complete LDO latency. |
| EfficientLoFTR: 40.1 ms full / 27.0 ms optimized at 640 × 480; RTX 3090 and Xeon Gold 6330; optimized uses mixed precision and removes dual-softmax. | A measured complete matching pipeline on ScanNet pairs. [Paper Appendix D](https://arxiv.org/html/2403.04765v2#A4) | Current code, actual keyframes, candidate budget, and target Windows/GPU dependencies. |
| RoMaV2: 30.9 pairs/s and 4.8 GB with custom correlation kernel; RoMa 18.5 pairs/s and 4.7 GB; H200, batch eight, roughly 640-square images. | Batch throughput and reported memory in that comparison. [Paper Table 8](https://arxiv.org/html/2511.15706v3#S4.T8) | Single-pair latency and precise/default resolution memory. These figures cannot be converted into a target-machine guarantee. |

LightGlue saves extractor work when a cached historical frame is matched to many queries. Pair-dependent transformed features from detector-free matchers are not interchangeable with a global retrieval descriptor. Cache design must follow the chosen model; none of these interfaces promises a shared global place descriptor head. This is an inference from the published interfaces and architectures above.

All runtime choices should be compared at a fixed candidate list initially. Report feature extraction separately from per-pair matching, p50/p95 latency, peak allocated GPU memory, host feature-cache size, and accepted geometric evidence. Then evaluate the complete retrieval → local matcher → proposal pipeline. More match density may increase downstream geometric work even if the neural matcher is faster.

Pin source revisions, checkpoints, hashes, preprocessing, precision mode, resolution, thresholds and random seeds in any future benchmark. RoMa's sampling and RANSAC are stochastic, and the current repository explicitly notes differences from its original experiment implementation. Published benchmark results are not evidence that the checked-out version reproduces them locally. [RoMa reproducibility note](https://github.com/Parskatt/RoMa#reproducibility)

## Confidence, geometry and training labels

**Scores require separate interpretation.** LightGlue's match score is derived from similarity and matchability; its early-stop token confidence predicts agreement with the final-layer assignment, not the probability of physical correspondence. EfficientLoFTR's optimized mode removes dual-softmax, and the demo applies an ad hoc normalization to `mconf` for visualization. Do not carry one numeric threshold between full/optimized models or matcher families. [LightGlue prediction code](https://github.com/cvg/LightGlue/blob/main/lightglue/lightglue.py), [LightGlue confidence supervision](https://arxiv.org/html/2306.13643v1#S3.S4), [EfficientLoFTR demo](https://github.com/zju3dv/EfficientLoFTR#match-image-pairs-with-efficientloftr)

RoMaV2 predicts overlap and positive-definite 2 × 2 precision matrices for **image-coordinate residuals**. Its covariance supervision is restricted to covisible regions with residuals below eight pixels. These estimates are not the same as LDO's camera/world XYZ covariance, stereo-depth uncertainty, or an absolute loop probability. If used, invert/map coordinate uncertainty correctly, then propagate it through the appropriate geometry and evaluate calibration on held-out data. [RoMaV2 paper, refinement](https://arxiv.org/html/2511.15706v3#S3.S3)

**Recommended calibration protocol:** freeze model and preprocessing; use disjoint development and test sequences/places; retain hard negatives with repeated structures and low-overlap pairs. Bin match scores against supported/contradicted evidence on the testable subset, and report testable coverage alongside precision. Fit any score-to-probability mapping on development data only. Report loop-level calibration separately using independently labeled revisit events. Thresholds should target false proposals per unit traversal/time and recovered events, not a convenient average confidence. These are proposed LDO practices rather than claims of published calibration guarantees.

**Preserve unknown depth.** The active [feature XYZ policy version 8](feature-xyz-evaluation.md) labels each correspondence supported, contradicted or untestable. Missing/unreliable depth is untestable and must not become a negative training label. Supported = geometrically supported under that checker and its uncertainty assumptions; contradicted = conflicting numerical evidence, not a perfect semantic oracle.

For future training, build positives from reliable, mutually visible projected points and independently justified negatives from reliable geometry. Mask unknown/occluded/border/invalid-depth observations out of match-supervision losses unless another trustworthy label source supplies evidence. Glue Factory explicitly accepts valid-depth masks and separate positive/negative thresholds; LightGlue's published supervision uses two-view reprojection and consistent depth. The existing XYZ verdict cannot be inserted wholesale into those losses without specifying projection, visibility, uncertainty and ambiguity rules. [Depth matcher source](https://github.com/cvg/glue-factory/blob/main/gluefactory/models/matchers/depth_matcher.py), [LightGlue supervision](https://arxiv.org/html/2306.13643v1#S3.S4)

Pseudo-depth from the current pretrained stereo system is useful evidence, but its errors can correlate with learned image matching. Evaluate missing-depth rates and any dependence on score, texture and range. Keep untestable counts visible rather than improving reported precision by silently dropping difficult observations. A two-view epipolar diagnostic can be added as auxiliary evidence without redefining the existing XYZ-only verdict.

## Reuse before training

Pretrained inference requires no LDO-specific training. Domain-specific fine-tuning is a later option if frozen-model experiments expose a reproducible limitation. EfficientLoFTR provides training code; Glue Factory provides custom-feature LightGlue training; original RoMa provides training experiments. Current RoMaV2 source exposes inference only, and MatchAnything's current landing README still promises training code later. [EfficientLoFTR training](https://github.com/zju3dv/EfficientLoFTR#training), [Glue Factory training](https://github.com/cvg/glue-factory#training), [RoMa training](https://github.com/Parskatt/RoMa#training), [RoMaV2 source](https://github.com/Parskatt/RoMaV2/blob/main/src/romav2/romav2.py), [MatchAnything release](https://github.com/zju3dv/MatchAnything)

MatchAnything's authors report pretraining on mixtures of multiview, video, synthetic warp and synthetic modality data, using 16 A100-80 GB GPUs for approximately 4.3 days (ELoFTR) or six days (RoMa). LDO should reuse the released result, not reproduce that foundation pretraining as its first experiment. The published dataset list does not itself prove that EuRoC, related imagery, or evaluation places are absent from every upstream pretraining stage. [Author training description](https://zju3dv.github.io/MatchAnything/)

The first concrete selection gate should therefore be: **does a frozen matcher recover more independent geometric evidence for difficult revisits at the same false-proposal rate and within the measured compute budget?** Resolve that question before a learned loop-score head, ORB-specific adaptation, or detector fine-tuning adds another source of uncertainty.
